Manaoke Song Builder — how a new song moves through the machine

One orchestrator (tools/songcraft/manaoke_build.py) walks a fixed 19-step DAG. Each step is a runner function that shells out to the right tool in the right Python env. Per-song state lives in builds/<key>.build_state.json; the denmoku dashboard just renders that file.

Drive it: run <key> <step> for one step, or run <key> --auto to walk every auto-able step and halt at the first gate or human-owned step.

assemble_page.py clones the current production page verbatim and swaps only data + palette + paths: injects data.json/manifest, splices LINE_TR/LINE_EXPLAIN literals, retargets YouTube id / titles / slug / og / canonical / chip, samples the cover for the fully-universal palette (field-c1/2/3/hi, fb blooms, body gradient), writes per-song _redirects, repoints fonts. Why assemble runs BEFORE audio
content_to_data.py (inside assemble) emits builds/<key>.audio_jobs.json — the exact clip list the audio steps consume. No jobs file → nothing to render. Re-running assemble regenerates index.html, so drill_concat + version bump must re-run after.
Faithful clone, gated
parity_audit.py runs inside assemble and hard-fails if the page diverges from the template anywhere outside the known per-song regions. A song page is the prod page with swapped data.

Gates halt the auto-walk
In do_run(--auto), a runner that returns not-ok sets the step blocked and breaks the loop. Auto=True steps with no wired runner refuse to silently skip — they stop loudly. That's the honesty guarantee.
Lean deploy model
The build dir ships only index.html · data.json · tts_manifest.json. Audio/pitch live once in _assets/<song>/; a Worker (folder = deploy-dir prefix) routes /songs/<dir>/audio/* there. Asset folder name MUST equal the slug prefix.

How the code actually executes

Orchestrator loop

manaoke_build.py holds a canonical STEPS list (19 dicts: key, owner, auto flag, env-specific cmd). A RUNNERS map binds each step key to a Python function.

do_run(key, step, auto): targets = # --auto → every auto & not-done step for step in targets: runner = RUNNERS[step.key] ok,msg = runner(st) # shells out step.status = 'done' if ok else 'blocked' save(st); write_dashboard() # live dot flip if not ok and auto: break # gate stops walk

Each runner is a thin wrapper that subprocess.runs the real tool in the correct interpreter: parler (demucs / CTC align / Kokoro / whisper), qwentts (pitch), plain python3 + ffmpeg (assemble, drill, validate, kits).

State is a single JSON per song: builds/<key>.build_state.json. On load, _sync_steps reconciles it against the code's STEPS so a reworded step or a new DAG entry reaches already-init'd songs.

Surfaces & entry points

CLI — the source of truth:

manaoke_build.py init <key> ... # create state manaoke_build.py run <key> assemble # one step manaoke_build.py run <key> --auto # walk to next gate manaoke_build.py rebuild <key> --why <sha8> manaoke_build.py dash # regen dashboard

denmoku dashboard (builder/index.html, file://) — a searchable album-art grid; tap a jacket → per-song Build + Gradient tabs. It only renders build_state.json + composes the copy-paste commands; Claude Code runs them. No local server.

Rebuild machinery — <folder>.deps.json content-hash manifests let rebuild --why <clip> re-run only what a changed input touches; the dashboard shows stale/current chips per song.

The one ordering rule that isn't obvious from the step numbers

The DAG is not strictly linear by index. assemble (6) runs before the audio steps (7–10) because content_to_data.py — invoked inside assemble — is what writes the audio job list. drill_concat (12) then runs after the clips exist, and pitch (11) slots alongside. So the real dependency spine is: source → sync → author → assemble (emits jobs) → audio → pronunciation QA → drill_concat → enrich → validate gate → ship. Re-running assemble regenerates index.html, so drill_concat + version-bump always re-run after it.
